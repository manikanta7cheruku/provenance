# ADR-0055: Production deployment, security hardening, backups and your own data

Status: Accepted (checkpoint 3.7).

## Context
Everything built so far runs on a laptop. Putting real people on it needs: a way to run it that is safe by default and repeatable, protection that does not depend on remembering things, a way to get the data back after a disaster, and the promises the privacy policy makes (a copy of your data, deletion) kept in code, not in good intentions. The risks are a deploy that cannot be undone, a configuration that quietly weakens security, secrets that cannot be rotated without losing data, backups nobody has restored, a deletion that leaves rows or files behind, and drills that only exist on paper.

## Decision

**One machine first, with the same images that CI builds (stage 1 of production-operations.md).** `compose.prod.yaml` runs a proxy, the web app, the API, the worker and the database. Only the proxy listens on the host (80 and 443) and gets its own certificate. Images are built from `infra/docker/*.prod.Dockerfile`: the API image is multi-stage (a build stage with `uv`, a runtime with only the installed environment, the PDF engine's libraries and a non-root user), the web image is an unprivileged nginx with the built files. Containers run read-only, with all capabilities dropped, no new privileges, memory limits, restart policies and rotated logs. Images are tagged with the git commit. Every secret is required by the compose file: a missing one stops the stack.

**Deploys are a script with a gate at each step.** `deploy/deploy.sh` builds, takes a backup, migrates as the owner role, runs `check-config`, starts the new version, waits for readiness and smoke tests it from outside. A failed configuration stops before anything new runs; a failed start or smoke test rolls back to the previous version (and says plainly when there is none). Migrations stay compatible with the code before them, so a rollback never needs the data rolled back.

**Safe configuration is checked, not remembered.** Settings refuse to start in production with placeholder secrets, plain http, no mail, or no token key. `pv_api.cli check-config` goes further, against the running database: https origins, a writable file store, the application role being unable to bypass Row Level Security, forced Row Level Security on every table that holds a person's data (the task queue is a named system table), and warnings for the decisions that belong to the owner (open sign-up, no model, no spend ceiling).

**Connector tokens have their own key ring.** Tokens used to be sealed with a key derived from `SECRET_KEY`, so rotating that would disconnect everyone (C-122). New values are `v2.<keyid>...`, sealed with the first key of `TOKEN_ENCRYPTION_KEYS` and opened with any key in the list; old `v1` values still open. Rotation is: new key first, keep the old, deploy, run `reseal-tokens`, remove the old. Production requires the ring.

**Backups are a script and a drill.** `deploy/backup.sh` writes a compressed database dump and an archive of the stored files with checksums and a manifest, and removes backups older than 30 days. `deploy/restore.sh --drill` restores into a scratch database next to the live one and checks the migration, the table count, forced Row Level Security, the application role's privileges and the vector extension; `--replace-live-data` is the real restore. Both were run. Copying backups off the machine is not automated yet, so nothing here is called disaster recovery until it is (C-160).

**Your data is yours, in code.** Settings has a copy of your data (one JSON file of what you put in, not your password, sessions, tokens or uploaded files) and account deletion. Deletion takes a password and typed words, refuses to remove the only administrator, signs the person out everywhere, makes the account inactive and queues a durable task owned by no one (it must outlive the user row). The task removes every stored file first, then the stray rows the foreign keys cannot reach (rate limit counters named with the id, the address in a bound invite, a queued email), then the user row; every table that holds the person's data cascades from it. It is safe to run again, retries on a storage error, and on its last attempt marks itself failed and deletes nothing rather than half delete. A minimal record (no person in it) says that a deletion happened. A test walks every foreign key to users and every table with an owner column, so a table added later that would block or miss deletion fails the build.

**Public documents.** A privacy policy and terms of use at `/privacy` and `/terms`, linked from sign-in and Settings, written to describe what the product really does (including the backup window and the model provider). They are a draft until a lawyer has read them, and each page lists what is open before launch.

**Supply chain and images in CI.** `pip-audit` and `npm audit` run on what ships (they found two real vulnerabilities in pinned packages, now upgraded), and an `images` job builds the production images, checks that the API image runs as a normal user with no development tools, and validates the production stack file.

**Drills are run and written down.** `docs/operations/drills.md` records what was broken on purpose and what happened, including the three defects the drills found (the web container caching an old API address, a wrong belief that rotating the application secret signs people out, and a restart that does not apply to a manual kill).

## Alternatives considered
- **Kubernetes or a managed container platform now.** Rejected for stage 1: one machine is enough for the first users and keeps the rollback, restore and cost simple. The images are the same, so moving later needs no rewrite.
- **A managed database with point-in-time recovery.** Preferred for later (C-159). It tightens the recovery point from a day to minutes. It is a hosting decision for the owner.
- **Object storage (R2) now.** Deferred (C-40). The storage layer is a Protocol and a volume works for one machine; a bucket needs an account and an S3 client that could not be verified here.
- **Sessions as signed cookies.** Not changed: sessions stay database rows, which can be revoked one by one or all at once.
- **Soft delete with a grace period for accounts.** Rejected for now: the privacy policy promises deletion, and a grace period would need a second state and a purge job. Asking twice is harmless and there is no undo.
- **A third-party service for TLS and DDoS protection in front.** Left to the owner at launch.

## Consequences
- A deploy is one command and a bad one stops itself. A full rollback takes about 16 seconds.
- A person can leave with a copy of their data and can delete everything, and a test proves nothing of theirs is left.
- The host, the domain, the mail provider and the model plan are the owner's to provide; until then the stack has been run only on a laptop.
- Real TLS certificate issuance, real mail and real load are not exercised until the real host exists.

## Evidence
Unit tests: the key ring (a v2 round trip naming its key, v1 still opening, rotation with an old key behind a new one, a lost key refusing, binding to context, tampering refused, key checks), production settings (the token key required, placeholders refused, duplicates and short keys refused), and the readiness checks (a complete production configuration is clean, a development one fails the right checks, decisions are warnings, no check prints a secret, a broken storage path and an unreachable database are failures not crashes). Integration tests with the real database: the readiness checks pass on the real database and catch a table planted without forced security, token rotation end to end (old token re-sealed, still working after the old key is dropped, an unreadable token counted and left alone), the production security headers, hidden API documentation, secure host-prefixed cookies and the origin check, the incident command signing everyone out, and the proof that rotating the application secret alone does not; the account tests: a copy of your data (contents, no secrets, no one else's data, sign-in required), deletion (password and words, CSRF, signed out everywhere, asking twice, the last administrator, rate limit, audit) and the deletion proper (every foreign key to users and every owner table empty, files gone, strays gone, no email in audit, a bystander untouched, a record naming no one, running again, a storage error retrying and removing nothing early, a last attempt marked failed with the data kept). Browser tests with axe in light and dark and a phone, and the entire browser suite run a second time against the production stack (nginx security headers over TLS). The production stack was built, started, smoke tested (15 checks), deployed twice, rolled back, stopped by a failed configuration, and its backup and restore were run (docs/operations/drills.md).
