# ADR-0029: Resume storage, parsing and profile entries

Status: Accepted (checkpoint 1.6). Builds on [ADR-0015](0015-postgres-rls-as-defense-in-depth.md), [ADR-0022](0022-queue-semantics-and-system-tables.md) and [ADR-0026](0026-deterministic-scoring-and-learned-ranker.md).

## Context
The profile is the evidence base for every later verdict. It starts from a resume, a file written by someone else, in a format designed to be shown and not parsed, that we must treat as hostile. A student must be able to see what was read, correct it, add what is missing, and delete everything. Free-tier model prompts may be used for training by the provider, so only the owner's own test data goes through the model until a paid tier is chosen (ADR-0027).

## Problem
How do we accept an untrusted document, turn it into structured entries with a model, and keep the result honest, correctable and safe?

## Options considered
| Question | Options | Result |
|---|---|---|
| Upload transport | multipart form, raw body | Raw body with the name in a header. No multipart parser, smaller attack surface. Content-Type is ignored |
| File type | trust name or Content-Type, sniff the bytes | First bytes decide (`%PDF-` or ZIP). A DOCX must also be a safe archive with the expected parts |
| Where files live | in the database, local disk behind an interface, object storage now | Local disk behind `FileStorage`. R2 or S3 replaces it in 3.7 with no caller change. Keys are generated by the server |
| Where parsing runs | in the request, in the worker | Worker, as a queue task with a workflow run. The request returns at once |
| Reading DOCX | python-docx, standard library plus defusedxml | Standard library `zipfile` plus `defusedxml`, so every limit is ours (entries, total size, ratio, XML bytes) |
| Reading PDF | pypdf, other | pypdf, with page and character caps before any text is used |
| Model output | free text, validated JSON | One call that must match a Pydantic schema, one retry whose feedback names field paths and error kinds and never quotes a value |
| Trusting the model | accept entries as returned, check them in code | Every entry is cleaned by `pv_domain.profile` (unknown fields discarded) and must be grounded: the words of its main field appear in the resume text. Others are dropped and counted |
| Entry shape | free JSON, typed specs | Typed specs in `pv_domain.profile`, shared by the API and the parser, and served to the browser which draws its forms from them |
| Resumes per user | many, one | One. To change it, delete and upload again. Profile entries stay |
| Re-parse | replace everything, replace nothing, replace only untouched | Replace only entries a parse created that the person never edited. Edits and hand-added entries are kept, and a parsed entry that matches one of them (by identity key, which survives edits) is skipped |

## Decision
1. **Upload.** `POST /api/v1/resume` takes the raw bytes (5 MB cap, enforced by the middleware and again while streaming), the percent-encoded name in `X-Filename`, a CSRF token and a session. The type comes from the first bytes. The file is written to storage under a random key (`resumes/<32 hex>`), then the row, the workflow run and the `parse_resume` task are created in one transaction. If the transaction fails the file is deleted.
2. **Storage.** `FileStorage` (put, get, delete, exists). `LocalDiskStorage` resolves keys against a root, refuses anything that does not match the key pattern, writes atomically and sets mode 0600. There is no public URL. Download is `GET /api/v1/resume/file` for the owner only, `attachment`, `no-store`.
3. **Parsing in the worker.** Steps: read file, extract text, structure profile (one model call, one guided retry), save profile. Each step is recorded in `workflow_steps` with counts and timings only. Every model call goes to `llm_calls` with the prompt version and a content hash, never text.
4. **Failures are results.** A failure the user can see (unreadable file, encrypted, too many pages, no text, model gave nothing usable, AI not configured) marks the resume failed with a short code, ends the run, and completes the task. Only transient trouble raises `TaskFailure` and is retried with backoff, and on the last attempt it becomes a visible failure too.
5. **Idempotency.** A task for a deleted resume or an older parse generation does nothing. Saving replaces only unedited parse-created entries.
6. **States.** `parse_status` (uploaded, parsing, parsed, parse_failed) and `review_status` (pending, confirmed) are stored. The user-facing state (uploaded, parsing, parsed, needs_correction, confirmed, failed) is derived by `pv_domain.resume.resume_ui_state`, with "needs correction" computed from the current entries so it updates as the person edits. The browser adds Idle and Uploading.
7. **Entries.** Eight types with typed fields, dates as `YYYY` or `YYYY-MM`, links as http or https only, lists one item per line. Strict for people (field-level messages), lenient for the model (invalid optional values dropped). Each entry stores `source` (resume or user), `user_edited`, `source_key` and `position`. The screen says "From your resume" or "Added or edited by you".
8. **Preferences.** One typed row per user (target roles, authorized countries, sponsorship need, locations, relocation, remote preference, employment types, minimum pay with currency, exclusions) so the eligibility engine (1.8) reads columns, not text.
9. **Isolation.** `resumes` and `profile_preferences` use the same RLS policy as `profile_entries`, enabled and forced. Isolation tests include raw SQL.

## Why
Each check sits where it is cheapest and hardest to bypass: the bytes decide the type, limits stop bombs before parsing, the schema and the grounding check stand between the model and the database, and the person has the last word through editing. Making parse failures into results gives users a message and a next step instead of a task that dead-letters.

## Consequences
- Grounding proves a name appears in the text, not that a claim is true. A hostile resume can make the model emit an entry whose words do appear in the resume (a unit test documents this limit). The person reviews every entry, and claim-level checks arrive with tailoring (2.4).
- Resume text is sent to the model provider. On a free tier that may be used for training, so only the owner's own data is allowed until a paid tier with no-training terms is in place.
- Scanned image resumes are not read (no OCR). The error says so.
- Orphaned files are possible if storage deletion fails after the row is gone. The key is logged and a sweep is a 3.7 task.
- API and worker share the storage volume in Compose. In production this becomes object storage.

## Scale analysis
| Users | Posture |
|---|---|
| 10 | One worker, local volume |
| 100 | Several workers sharing the volume or a bucket. Provider rate limits become the bottleneck (`LLM_MIN_INTERVAL_SECONDS`) |
| 10,000 | Object storage, parse concurrency limits, per-user quotas (3.3), cost review per parse |

## Revisit when
OCR is needed, the model starts dropping many valid entries (the dropped count shows it), multiple resumes per user are wanted, or storage moves to object storage.
