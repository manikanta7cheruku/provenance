# AI-Specific UX Patterns

Status: Decided (Phase 0 amendment). These patterns are part of the product architecture. They decide which fields the data model must store, because a screen cannot show what the system did not record.

## 0. Vocabulary (do not mix these)

| Term | Describes | Values |
|---|---|---|
| Claim origin | Where a displayed statement comes from | posting, evidence, inference, suggestion |
| Evidence kind | How a piece of evidence relates to a requirement | direct, inferred, missing, conflicting |
| Verdict | The conclusion for one requirement | met, partial, not_verified, conflicting, blocker |
| Confidence band | How sure the system is, computed by code | High, Medium, Low, Not enough evidence |

An inferred piece of evidence (evidence kind) is shown as an inference (claim origin). Values are stored once, in [data-model.md](../architecture/data-model.md) section 8.

## 1. Fact, inference, suggestion

Every statement on an analysis screen carries an origin, and the screen says so.

| Origin | Label | Meaning | Visual treatment |
|---|---|---|---|
| Posting | From the posting | Text or value extracted from the job description, with its source span | Quote style, linked to the span |
| Evidence | From your evidence | A fact in the user's own evidence, with its source record | Solid marker, evidence chip |
| Inference | Inferred | A conclusion the system drew from evidence | Dashed outline, "Inferred" label, shows its inputs |
| Suggestion | Suggested by AI | Generated text the user has not accepted | Distinct tint, "Suggested" label, always editable |

Never present an inference or suggestion with the styling of a fact.

## 2. Evidence provenance

- Every verdict opens to its evidence: record type (project, work, education, user answer, repository), title, the relevant excerpt with the matching span highlighted, and the date added.
- Evidence chips are links to the full source entry in the profile.
- A verdict with no evidence says "No evidence found", never an empty cell.
- Evidence the user can edit has an "Edit" route back to the profile.

## 3. Requirement-level explanations

Each requirement row answers, in order:

1. What does the posting require (quote)?
2. Do you meet it (Met, Partial, Not verified, Conflicting, Blocker)?
3. What supports that (evidence kind and chips)?
4. How sure is the system (confidence band)?
5. What is missing, if anything?
6. What can you do next?

## 4. Confidence and uncertainty

- Coarse bands only: High, Medium, Low, plus "Not enough evidence". No percentages.
- Bands are computed by code from evidence properties (kind, count, exactness of match, whether the requirement is required), not from the model's self-reported confidence. The rules are versioned configuration.
- Uncertainty is shown as a reason: "Only one project mentions this", "Evidence is indirect". A band without a reason is not allowed.
- "Not verified" is not "No". The wording says the system found no evidence, not that the user lacks the skill.

## 5. Why did I get this score

- The top of the screen states the recommendation and the sentence behind it: "Strong match: 9 of 11 required requirements supported."
- The Score tab lists each dimension with its inputs, weight and effect in words. Example: "Required coverage: 9 of 11 supported. Seniority fit: the role asks for 0 to 2 years, your evidence shows 1.2. Posting recency: 3 days."
- Explanation sentences are generated by code from stored inputs using templates, not as free LLM prose.
- Hard gates are shown separately from soft fit and say why they apply. A job that fails a gate shows the gate, not a score.
- The scoring version is visible so a past result can be reproduced.

## 6. Agent and run progress

- Show what the system did in operational terms with persisted counts: "Extracted 11 requirements", "Retrieved 14 evidence items", "Verified 9 requirements", "2 need your input".
- Never show internal reasoning text or invented percentages.
- A bar is drawn only when the denominator is stored.
- Results appear as each requirement finishes. A partially analyzed job is labeled "Partial: 6 of 11 requirements checked".
- When the agent needs the user, the state is "Waiting for you" with the specific question and answer controls. The answer becomes new evidence and the UI says so.

## 7. Editable AI output and user control over AI-generated changes

- Generated content is labeled "Suggested" until accepted.
- Edit in place. The original suggestion stays available to compare.
- User edits are recorded as user-authored. Regeneration never overwrites a user edit without confirmation.
- Accepting changes the label to the user's content and keeps its evidence links.
- Nothing generated is applied to the user's materials without an explicit accept. Reject, edit and regenerate are always available, and any change can be reverted to the original.

## 8. Human approval checkpoints

Consequential actions use a confirmation that:

1. Names the object ("Mark Acme AI, AI Engineer as applied").
2. States what will and will not happen ("Provenance does not submit applications.").
3. Offers a clear cancel.
4. Records actor and time.

Approvals in the product: approve for preparation, accept a tailored change, approve materials, mark applied.

## 9. Correction and retry flows

- Every verdict has "This is wrong". The user can attach evidence, mark the verdict incorrect, or answer a question. Re-analysis reruns only the affected requirement.
- Corrections are stored as feedback and feed evaluation.
- Failures offer Retry and state what is preserved. Permanently failed items explain the alternative (for example "paste the job description instead").

## 10. Grounding and evidence verification

- Generated claims (tailoring, preparation answers) show a verification state per claim: Supported, Not supported, Needs review.
- A not-supported claim cannot be approved. The user edits it, supplies evidence, or removes it.
- The verifier result shows which evidence supports each claim, so the user can check the check.
- The UI says "verified" only when code confirmed that the cited evidence exists and contains the basis for the claim.

## 11. Data the patterns require

Additive refinements to [data-model.md](../architecture/data-model.md). They do not conflict with the approved architecture, but they must exist in the schema from the migration that creates the tables.

| Pattern | Required data |
|---|---|
| Fact, inference, suggestion | `origin` on every displayed claim: posting, evidence, inference, suggestion |
| Evidence provenance | Evidence references with `source_type`, `source_record_id`, excerpt offsets |
| Requirement explanation | `requirement_verdicts.confidence_band`, `confidence_reason_code`, `missing_reason_code`, `next_action_code` |
| Score explanation | `scores.explanation`: per dimension inputs, weight, and effect text produced by code templates |
| Run progress | `workflow_steps` with persisted counters (`done`, and `total` where known) |
| Editable generated content | `user_edited` flag, original text retained on `material_claims` |
| Corrections | `feedback` entries linked to verdicts |
| Waiting for you | `pending_question` stored on the run with its answer schema |
