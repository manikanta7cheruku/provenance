# Threat Model

Status: Decided (Phase 0). Maintained through every phase.

## 1. Assets

| Asset | Sensitivity |
|---|---|
| Resumes, profile, evidence, preferences, work authorization | High personal data |
| Application materials and notes | High |
| Session tokens, password hashes, OAuth tokens, API keys | Critical |
| Job analyses and verdicts | Medium |
| Source and LLM provider credentials, and spend | High (financial) |
| Audit and security logs | Integrity critical |

## 2. Trust tiers

| Tier | Contents | Handling |
|---|---|---|
| 0 | Our code, config, schemas, prompts | Trusted. Reviewed and versioned |
| 1 | Authenticated user input and data | Validated, authorized, isolated per tenant |
| 2 | External content: job descriptions, fetched pages, repository content, CSV cells, company pages, LLM output | Untrusted. Never treated as instructions. Sanitized, size capped, schema checked |

LLM output is Tier 2 until validated by code.

Since checkpoint 1.8 a pasted job description is Tier 2 text that reaches the model. It is wrapped in nonce delimiters, the model's answer is checked by code that keeps only items whose quote is found in the posting ([ADR-0031](../adr/0031-job-paste-extraction-and-eligibility.md)), and eligibility is decided by code from those verified facts. A sentence inside the posting that tells the model what to do can change what is proposed, not what is trusted. Nothing acts without the person's approval.

From checkpoint 1.9 the evidence agent reads a person's own entries and their typed answers, and the requirement text, all treated as data between nonce markers. It has no write tool, no network tool and no way to name another person's rows: evidence is cited by labels that code assigned in the run, and a verdict is accepted only if its quoted words are found in the cited evidence ([ADR-0032](../adr/0032-evidence-agent-and-on-read-scoring.md)). A hostile posting could make the agent give a wrong verdict, but not one that cites something the person does not have.

The resume studio (checkpoint 2.1) takes rich text from the browser and turns it into HTML and a PDF. The browser's JSON is validated against a whitelist on every save and preview, no markup is stored, every string is escaped by one renderer, the preview frame has no scripts, and the PDF engine can read only the shipped fonts. A hostile document can therefore produce odd text but not script, a remote image or a file read ([ADR-0033](../adr/0033-resume-studio-document-and-saving.md)). The free canvas of checkpoint 2.2 adds positions and colors to that data. Both are numbers within the page or a name or a hex code, checked on the server, and each element's CSS is written by the server from those values and escaped for an attribute, so a position or color cannot carry markup or a URL ([ADR-0034](../adr/0034-free-canvas-editor.md)). Links (2.3) are the one place a document can carry an address. The mark accepts only https, http, mailto and tel, refuses whitespace, control characters, quotes and angle brackets, and requires a host for web addresses, on the server and again in the browser. The address is escaped into an `href` with `rel="noopener noreferrer"`, and a `javascript:` or `data:` address is refused with a message next to the text ([ADR-0035](../adr/0035-template-library-links-and-themes.md)).

## 3. Actors

External attacker, malicious authenticated user, malicious job poster (controls Tier 2 text), compromised dependency, curious insider or admin, accidental misuse.

## 4. Threats and controls (STRIDE style)

|---|---|---|---|
| T1 | Cross-tenant read or write (IDOR) | Identity from session only, repository scoping, Postgres RLS with FORCE, non-owner DB role, 404 on miss | Per-resource isolation tests, raw SQL test |
| T2 | Credential stuffing, brute force | Argon2id, per-IP and per-account rate limits, progressive delay and lockout, uniform error text | Rate limit tests, timing comparison |
| T3 | Session theft or fixation | Opaque random tokens, hash stored, httpOnly Secure SameSite cookies, rotation on login and privilege change, revocation on logout and password change | Cookie attribute tests |
| T4 | CSRF | SameSite cookies plus CSRF token on state-changing requests, Origin check | CSRF tests |
| T5 | Prompt injection via job text or repo content | Isolation of untrusted text, no tools in extraction, read-only user-scoped tools for the agent, schema validation, evidence required, length limits, content hash logging, no side effects triggered by content | Injection fixtures in eval and CI |
| T6 | SSRF through URL import, company research, GitHub fetch | Scheme allowlist, DNS resolve then connect to the resolved IP, block loopback, private, link-local, metadata, IPv6 equivalents, recheck each redirect, redirect cap, size and time caps, no cookies or credentials, egress isolation | SSRF suite including DNS rebinding simulation |
| T7 | Malicious file upload (resume, CSV, XLSX) | Type sniffing not extension only, size caps, parse in worker with resource limits, no macro execution, zip bomb limits, store privately, no inline serving. CSV and XLSX arrive in 2.8 | Fixture tests (unit and integration) |
| T8 | Stored XSS from job text or profile text | Treat as text, sanitize HTML, strict CSP, escape on render | XSS fixtures |
| T9 | CSV or XLSX formula injection in exports | Neutralize leading formula characters | Export tests |
| T10 | Password reset or verification token abuse | Short lived, single use, hashed at rest, uniform responses | Token tests |
| T11 | Cost abuse (LLM spend) | Quotas, daily caps, global spend ceiling, idempotency, budgets per run, kill switch | Quota and budget tests |
| T12 | Source terms violation | Registry gating, min poll intervals, no bypass features exist in code | Compliance review, registry tests |
| T13 | Secrets leakage | Env or secret manager, never in repo or images, log redaction, secret scanning in CI | CI scan |
| T14 | PII in logs | Structured logging with allowlisted fields, no resume text or full prompts | Log tests |
| T15 | Dependency compromise | Pinned versions, lockfiles, automated vulnerability audit in CI | CI audit |
| T16 | Admin overreach | Admin cannot browse private content without an explicit capability, and every such access creates an audit event | Authorization tests |
| T17 | Unsupported claims reaching a user or employer | Grounding verifier, user approval step, no submission capability | Verifier tests |
| T18 | Race and duplicate execution | Idempotency keys, unique constraints, transactional state transitions | Concurrency tests |
| T19 | Data loss | Backups, restore tests | Restore drills |
| T20 | Account deletion incomplete | Deletion workflow covering DB, object storage, caches, connector tokens | Deletion tests |
| T21 | OAuth token theft | Encrypted at rest, minimal scopes, revocation on disconnect | Connector tests |
| T22 | A tailored resume that claims something untrue, or text in a job or resume that tries to steer the suggestion model | The model only proposes. Code checks every claim (number, name, tool, job keyword) against the old wording and cited evidence, and a failing suggestion is blocked and cannot be accepted, even after an edit. Accept re-checks against current evidence. Labels assigned by code, so no unknown evidence can be cited. Only confirmed requirements are offered, the rest are marked do not claim. Job, resume and evidence sit between random markers and the prompt says they are data. Names, dates and headings are never offered to the model. Accept is a revision-checked save with a restore point | Verifier tests with invented numbers, tools and employers, integration tests for blocked, forged labels, accept re-check, edit re-check and isolation |
| T23 | A source is used against its terms, or a source is silently substituted for the one asked for | Sources are data with a compliance record (terms address, date read, reviewer) that expires. No source is enabled unless verified and in date, in code and as a database CHECK. Import only platforms have no adapter. The resolver never substitutes and says which source was used. Admin changes are audited. Terms are re-read on a schedule | Registry rule tests, CHECK test, resolver tests, admin audit test |
| T24 | Text in a typed search steers the model, or sets work authorization | The sentence sits between random markers and the prompt says it is data. The model only fills a structure, and code cleans it against allowed lists. Authorization is read from the profile only. Companies and sources are chosen by code | Injection test, intent cleaning tests, authorization test |
| T25 | Outbound fetching abused or failing: hammering a source, following a redirect to somewhere else, an oversize or hostile answer, stored markup, stale jobs shown after a source is no longer permitted | One fetch module: https and allowed hosts only, no redirects, size and time limits, no cookies. Addresses built from a fixed template and a checked board id, never from a person. Minimum poll interval per board, Retry-After obeyed, a circuit breaker per source. Parsers reduce everything to plain text and https addresses and skip what they cannot trust. Jobs are shown only while their source is enabled, verified and in date | Fetcher tests, parser tests with hostile input, breaker and interval integration tests, hide-on-expiry test |
| T26 | A private posting leaks to others through duplicate detection, or a wrong automatic merge hides a different job | A pasted posting is compared with public jobs on read, inside its owner's own request, and no public row refers to it. Only the owner's decisions are stored, under Row Level Security. Links between public jobs are edges with groups computed from them, so any link can be undone without loss, an undone link is never recreated, and different places, companies and levels are never linked | Privacy and RLS integration tests, matcher hard-rule tests, undo and split tests |
| T27 | A typed web address makes our server connect to a private network, a cloud metadata service or another internal place (server side request forgery, including DNS rebinding and redirects) | The API never requests an address. The worker checks the address by rules (https, port 443, no credentials, no numeric host, no internal name, no site that forbids automated reading), resolves the name once, requires every resolved address to be public, connects to the checked address with the name kept for the certificate, and checks every redirect hop again. Size, time and type limits apply. No cookies or credentials. Fetch errors are plain sentences and never include page content | Address rule tests for every encoding, pinning and rebinding tests, redirect tests, size, compression and deadline tests |
| T28 | A hostile spreadsheet (zip bomb, macro, entity expansion, formula, huge file) harms the server or the person | The kind comes from the first bytes. Entry count, uncompressed size, compression ratio, path and read caps. defusedxml. Macro and encrypted files refused unopened. Formulas are never calculated and the product never writes a spreadsheet. Rows, columns, cells and bytes capped. Parsing runs in the worker. The file is deleted when the import ends | Hostile file tests for each case, row limit tests |
| T29 | A person changes, reads or bulk-acts on another person's job decisions, notes or saved views, or an action is offered or accepted that the rules forbid (approving a job a hard rule rules out, a future applied date) | Decisions, their log and views are tenant data under Row Level Security and filtered by owner, and another person's job is not found. Every move goes through one function that decides both what is allowed and what is offered. Bulk moves check each job on its own and report others as not found. Saved views and list requests go through the same cleaning, so stored input is never trusted. The log holds no note text. Rate limits apply | Privacy and Row Level Security integration tests, transition tests for every combination, bulk tests, query cleaning tests |
| T30 | The shortlist email is sent to the wrong address, to an unverified one, too often, twice, or carries another person's job data or tracking | It goes only to the verified address of the account, read when the task runs and never stored in a task. A run is unique per person and time. A task for a time that is no longer the next one does nothing. The content is built from the person's own jobs under Row Level Security, as plain text with links only into the product and no images. Settings and sending are rate limited (manual sends 5 a day) and audited without the address | Selection and schedule tests, retry and stale task tests, unverified and privacy tests, email text tests |
| T31 | A draft states something untrue (an invented number, skill or employer), follows an instruction hidden in the job or the evidence, or leaks another person's evidence | A draft is made only from the evidence that supported a checked job, between markers the text cannot contain, with the unsupported requirements named only as things not to claim. Every claim is checked against that evidence and the job heading and the ones in neither are stored and shown. The check runs again on every edit. Nothing is sent anywhere and every screen says it is a draft. Drafts and their evidence are tenant data under Row Level Security | Claim check tests, prompt injection and marker tests, privacy and Row Level Security integration tests |
| T32 | A hostile picture harms the server (a decoder fault, a decompression bomb, a polyglot), leaks hidden data (camera, place, time), is read by another person, or is used to make the PDF task fetch something | The type comes from the first bytes and only JPEG, PNG and WebP are accepted (SVG and the rest refused by name). The size is read from the header and an oversized picture is refused before any pixel is decoded. Animated pictures, damaged pictures and every decoder warning are refused. The upload is never stored: it is drawn again as a new JPEG or PNG with no metadata and cut down. The file is private storage served only to its owner with `nosniff` and a sandbox policy. A document can only use its owner's pictures (strangers and deleted pictures get the same sentence), and pictures are embedded as data so rendering fetches nothing. Limits per person and per resume. Decoding in a separate process is carryover | Hostile file tests (bombs, polyglots, headers, animation, bad checksums), metadata removal tests, ownership and Row Level Security integration tests, PDF task ownership test |
| T33 | A saved theme is used to put an unreadable or unexpected value into a resume, to carry words or a picture from one resume to another, to reach another person's themes, or to exhaust storage | A theme is only a name, a font pair from our list and four hex colors, checked by the same function that checks a resume's style (readable text, a readable tint). It has no words, pictures or links. Applying copies values, so nothing follows a theme afterwards, and a resume checks its style again on save. Row Level Security and an owner filter on every statement, with another person's theme not found. At most 20 per person, rate limited writes, unknown fields refused, audit events without contents | Rule unit tests, ownership and Row Level Security integration tests, limit test, audit test |
| T34 | The GitHub sign-in is forged or replayed (cross-site request forgery, a stolen or reused code, a return meant for someone else) | A random single-use `state` bound to the person who started it, expiring in ten minutes, checked before GitHub is asked for anything. PKCE (S256) so a stolen code is useless. The code and state are removed from the address bar and history on arrival. The callback needs the session and the CSRF token. Starting again replaces the earlier sign-in | State, PKCE and single-use integration tests, an expired and a made-up state, the browser test that the address is cleared |
| T35 | The GitHub access token is stolen from the database, a backup or a log, or used for more than it should be | No OAuth scope is requested (public information only), the database refuses a stored scope. The token is sealed with AES-256-GCM, bound to the person, so a copied or changed value fails to open. It is opened only in the worker for the length of its calls and is never in a response, a log or an audit record. Disconnect deletes it and asks GitHub to revoke it, and it is deleted even if GitHub does not confirm | Encryption unit tests (tamper, context, another key), a moved-token integration test, tests that the token is absent from responses, logs and audit, the empty-scope check |
| T36 | GitHub, or something pretending to be it, makes the server contact another address (SSRF), or floods it with data | One gateway that contacts only the two configured hosts and refuses any other before the request is made, never follows a redirect, has short timeouts, reads at most a fixed number of bytes, and validates the form of every name that goes into an address. Every failure becomes one of five plain codes | Gateway unit tests (other host, redirect, unsafe names, capped bodies, odd answers) |
| T37 | Text in a repository (a name, description, README) injects script, markup or instructions into the profile, a PDF or a model prompt | Everything from a repository is cleaned (control and direction characters, tags, markup), capped and reduced to plain sentences, then validated by the same rules as a typed entry. It is stored as data for the person to read and edit, rendered as text, and nothing becomes evidence until the person chooses it. The evidence agent treats entries as quoted material, never as instructions. No live GitHub call happens during analysis | Rule unit tests with hostile repositories and READMEs, the hostile-text integration test |
| T38 | The model flatters, invents experience, an interviewer or a company process, or claims a question will be asked, and the person trusts it | Code decides what to prepare (priority, difficulty, what applies, the plan). The model sees every requirement with whether the evidence shows it, and only the evidence the check found, between markers it cannot contain. Every item is checked against the evidence it cited and the job's own words, and every claim in neither is stored and shown beside the item. An item with no cited evidence says so in a fixed sentence. The prompt forbids invented interviewers, processes, links and titles. Wording is hedged by rule and by a label on every list | Prompt and rule unit tests, an invented-fact integration test, the not-enough-evidence test |
| T39 | A message written for the person is sent, or contains something untrue about them | Provenance never sends anything. A message is a draft the person edits and copies. It is checked like an application draft (first person, only facts from the evidence), every edit is checked again, and writing again after an edit asks first | Message integration tests (edit, recheck, replace), the browser test that nothing is sent |
| T40 | One person's preparation, answers or mock interview reaches another, or an answer is logged | Row Level Security (enabled and forced) and an owner filter on all four tables, with another person's job or mock interview not found on every route. Audit records hold the action only. Task errors and logs never contain job or evidence text. An answer in a mock interview is stored only in the person's own row | Ownership tests on every route, the audit test, Row Level Security checks |
| T41 | A request takes more than a plan allows (two at once, a retry, a double click) | Check and charge run in one transaction under a per-person advisory lock, and each charge has a unique event key per month, so the same key is one unit | Concurrency and idempotency integration tests |
| T42 | A bad or missing plan row grants too much | Missing or invalid values read as zero, only an explicit null is unlimited, an inactive plan falls back to the default and then to all zeros, and the application role cannot write plans | Unit tests for bad rows, integration tests for fallback and for the role grant |
| T43 | One person's usage or plan is seen by another, or a person changes their own plan | Row Level Security enabled and forced on `user_plans` and `usage_ledger`, plan changes only through the operator command, and the upgrade route always refuses | Row Level Security checks, the upgrade route test |
| T44 | A payment is started or card data collected before a provider is chosen | Payments are a Protocol with only a disabled implementation. The screen has no buy control and the API returns 409 | Unit test for the disabled provider, the browser test that no buy control exists |
| T45 | A job posting plants a spreadsheet formula (=, +, -, @) that runs when a report is opened | Every text cell is neutralized in the domain (leading apostrophe), a workbook holds only inline strings and never a formula, and the writers drop forbidden characters again | Unit tests for every formula start in CSV, XLSX and DOCX, integration tests that plant the strings in a stored job and read the files back |
| T46 | Someone else downloads, lists or deletes a person's report | Row Level Security enabled and forced, an owner filter on every query, download only for the owner while ready and unexpired, anything else is not found, no public link | Ownership tests on read, download and delete, Row Level Security check |
| T47 | A report leaks evidence text a person did not mean to share | Quotes are off by default, dropped in the domain unless the flag is on, cut to 300 characters, and the screen says to keep the file private | Quotes off and on tests in the unit, integration and browser suites |
| T48 | A hostile or odd value makes a file that will not open, or a file that carries a macro or fetches something | Forbidden XML characters dropped, long cells cut, no macro parts and no external relationships written, a fixed timestamp for reproducible bytes | Real readers (openpyxl, python-docx, csv) open every file, tests that no macro or external reference exists |
| T49 | Reports are used to exhaust storage or the worker | Three being made at once, 20 asks an hour, the newest 20 kept, a 7 day expiry that deletes the file, a 500 job cap | Limit, expiry and cap tests |
| T50 | A failure log or audit record exposes job or evidence text | Errors carry a code only, audit holds the action only, the worker never logs job text | The failure test (text in the exception never reaches the row or run) and the audit test |
| T51 | The admin console becomes a way to read people's content | The console reads system tables only (tasks, workers, model calls, sources, audit, rate limits). Tenant tables have no admin exception. A test fails if the console's source names a tenant table | The no-tenant-table test and the 404 tests for non-admins |
| T52 | Cost or usage views identify a person | Cost is added up by model, operation and day. Accounts are counted, never named. The heaviest account is a share, not a name | The test that usage output holds no email or id |
| T53 | A person's run page exposes reasoning, text or raw errors | The inspector shows steps, counts (numbers only), model usage and plain sentences. An unknown failure gets a generic sentence. Another person's run is not found | The steps-counts test, the unknown-failure test and the ownership test |
| T54 | An alert is missed because a measurement is missing, or reads as healthy | A measurement not taken is None and fires nothing, and the screen says not measured. Critical alerts make the check command exit 1 | Unit tests for missing measurements and the command exit code tests |
| T55 | Trace lookups leak other people's work to an admin | Find a run returns tasks and model calls only (type, state, tries, redacted error, model, tokens). The queue never holds a job or resume text, and secrets are erased when a task ends | The trace integration test and the queue payload rules (ADR-0022) |
| T56 | Evaluation data contains real personal data, or leaks it | The dataset is synthetic (invented companies and roles, template text), a test checks it holds no email, link or phone number, and stored runs hold only metrics and synthetic case text | The dataset tests and the stored-run tests |
| T57 | A regression ships because nobody looked, or the baseline is edited to hide one | A deterministic gate fails the build on any metric outside its limit or worse than its baseline, a new metric with no baseline also fails, and a baseline change is a reviewed diff with a stated reason | The gate tests, including making grounding, eligibility and verdict acceptance worse |

| T59 | A model is trusted to judge a model, or a metric reports success on nothing | No model grades a model. Code and labels decide every number. ## 5. Blast radius analysis for a malicious job description

A posting can contain any text. Even if the model fully obeys it, the extraction call has no tools and returns only a schema validated object. The agent's tools are read only and scoped to the current user. No component can send email, run code, submit applications, or call arbitrary URLs on behalf of content. State transitions are made only by code. Therefore the worst realistic outcome is a wrong or low quality extraction, which evaluation fixtures and evidence requirements are designed to catch.
